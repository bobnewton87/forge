# Forge — Build Contract

This file is the single source of truth that all builders code against. If you need
something not covered here, make the smallest reasonable assumption, write it down in a
`// CONTRACT-NOTE:` comment at the top of your file, and keep going. Do NOT edit this file
or files owned by another builder.

## What Forge is

A flexible, day-to-day training app for one user (Bob). He's a former elite
marathoner (2:30 PR) who is now lifting to get **ripped and bigger**. He has a demanding
job, so every day he wants to:

1. Say **how much time** he has (15–90 min), **where** he is (home / Crunch gym / hotel /
   office), and optionally **which muscles** he wants to hit, or just ask "what should I do?".
2. Get a workout built for that time and equipment, with exercises picked for his
   **sculpt goals** (e.g. "bigger biceps peak", "wider lats", "capped delts").
3. Or pick a **Crunch class** (Crunch Allen, TX) or any cardio (row, bike, run, stairs…) instead.
4. Log it quickly. The app tracks per-muscle volume and recovery, and recommends what to
   train next based on how long it's been, weekly set targets, and his priorities.

This replaces "Iron Runner" (`~/workout`), a fixed 48-week plan app. Forge has **no fixed
calendar**. Nutrition (carb cycling) is optional and off by default.

### User facts to bake in
- Home equipment: trap bar + plates + crash pads, adjustable bench (flat/incline/decline),
  adjustable dumbbells. NO squat rack, NO pull-up bar, NO cables at home (bands optional,
  user can toggle them on).
- Gym: Crunch Allen (510 N Watters Rd, Allen TX). Full commercial gym: cables, machines,
  barbells, smith, racks, pull-up/dip, cardio machines, classes.
- **Never program barbell back squats.** Quads: leg press, hack squat, goblet,
  Bulgarian split squat, lunges. Trap bar deadlift is the preferred posterior-chain
  compound. Use barbell only when it clearly beats the DB/cable/machine equivalent.
- Priority muscles: **triceps (≥12 sets/wk)**, **side delts (≥12 sets/wk)**, **abs (~6+ sets/wk)**,
  plus upper chest and lats for the V-taper. Legs are already strong and low priority
  (maintenance volume only).
- Progression must be **performance-based** (double progression), never arbitrary weekly
  bumps. Always show "Last time: 40×10, 10, 9" next to today's target.
- Takes Adderall (appetite suppression). Nutrition tips should account for that.
- Not a lifting expert: every exercise needs short form cues and a YouTube search link.

## Tech stack (non-negotiable)
- Vanilla JS **ES modules**, no build step, no npm dependencies, no frameworks.
- Static site hosted on GitHub Pages at `https://bobnewton87.github.io/forge/`. Must work
  offline as an installable iOS PWA.
- All `js/data/*`, `js/engine/*`, `js/classes/classify.js` modules must be **pure and
  DOM-free** so they can be imported in Node 20 for tests (`node --test test/`).
- Use relative imports with explicit `.js` extensions.
- Persistence: `localStorage` via `js/store.js` only. No other module touches localStorage
  (except the Iron Runner importer, which reads `ir_*` keys).
- Mobile-first: designed for a 390px-wide iPhone screen, big tap targets, dark theme.
- Dates: local calendar dates as `'YYYY-MM-DD'` strings. Use helpers in `js/util.js`.

```
forearms:   forearms

glutes:     glutes, glute_med

```

Exports:
```js
export const REGIONS = { [regionId]: { id, name, group, description, recoveryHours, weeklySets:{min,max}, priority } }
  // priority: 0.5 (maintenance) | 1 (normal) | 1.5 (priority). Defaults from user facts above.

  // split sensibly across the group's regions).
```

## 2. Sculpt goals (`js/data/sculpt.js`)

These are aesthetic goals the user can turn on ("bigger biceps peak"). They bias exercise
selection and volume. Be **evidence-honest**: say plainly when something is mostly genetic
(peak shape, muscle insertions) or a myth ("inner chest", spot-reducing fat), while still
giving the best practical emphasis.

```js
export const SCULPT_GOALS = { [goalId]: {
  id, name, group,            // e.g. 'biceps_peak', 'Biceps Peak', 'biceps'
  regions: { [regionId]: weight },     // which regions to emphasize (weights 0-1)
  emphasisTag: 'biceps_peak',          // matches Exercise.emphasis tags
  summary,                             // 1-2 sentences
  science,                             // honest paragraph: what's trainable vs genetic
  tips: [string],                      // practical programming tips
  extraWeeklySets: number,             // volume added to the regions when this goal is on
}}
export const DEFAULT_SCULPT_GOALS = ['triceps_mass','shoulder_width','six_pack','lat_width','upper_chest']
```
Cover at least these (more is welcome): biceps_peak, biceps_width (short head + brachialis),
arm_thickness (brachialis/brachioradialis), triceps_mass (long head), triceps_horseshoe
(lateral head), shoulder_width (side delt), capped_delts (all 3 heads), rear_delts,
lat_width, back_thickness, upper_chest, chest_fullness, traps_yoke, forearms, six_pack,
obliques_vline, v_taper, glutes, calves, quad_sweep, hamstrings.

## 5. Exercises (`js/data/exercises-upper.js`, `js/data/exercises-lower.js`)

Each file does `export default [ ...Exercise ]`. `js/data/exercises.js` merges them:
`export const EXERCISES` (array), `export const EX_BY_ID` (map), `export function getEx(id)`.

```js
Exercise = {
  id: 'db_incline_curl',           // snake_case, unique across BOTH files
  name: 'Incline Dumbbell Curl',
  equipment: ['dumbbell','adjustable_bench'],   // ALL required (AND). Omit 'bodyweight'.
  alt: ['...exercise ids that train the same thing with other equipment'],  // optional
  category: 'compound' | 'isolation',
  pattern: 'horizontal_push'|'vertical_push'|'horizontal_pull'|'vertical_pull'|'hinge'|
           'squat'|'lunge'|'elbow_flexion'|'elbow_extension'|'lateral_raise'|'rear_delt'|
           'fly'|'shrug'|'core_flexion'|'core_anti'|'rotation'|'calf'|'hip_extension'|
           'knee_flexion'|'knee_extension'|'abduction'|'adduction'|'carry'|'wrist'|'conditioning',
  muscles: { biceps_long: 1, biceps_short: 0.6, brachialis: 0.4 },
     // volume credit per working set. 1 = prime target, 0.5 = strong secondary,
     // 0.25 = minor. Only REGION ids from §1.
  emphasis: ['biceps_peak'],       // sculpt goal emphasisTags this exercise is GOOD for
  repRange: [8, 12],               // default hypertrophy range
  unit: 'each' | 'total' | 'bodyweight' | 'seconds',
     // each = weight per dumbbell/hand, total = loaded bar/stack, seconds = timed hold
  step: 2.5,                       // smallest sensible weight jump (DB 2.5 or 5, machine/cable 5, trap/barbell 5-10)
  secPerRep: 3,                    // tempo estimate for time budgeting
  setupSec: 60,                    // time to set up before first set
  unilateral: false,               // true → sets are done per side (doubles time)
  difficulty: 1 | 2 | 3,           // 1 beginner-friendly
  fatigue: 1 | 2 | 3,              // systemic cost (trap deadlift 3, curls 1)
  cues: ['3-5 short form cues'],
  why: 'one sentence on what this is uniquely good for / which head it biases',
  yt: 'https://www.youtube.com/results?search_query=...+form',
  tags: ['home','gym','travel','superset_friendly','stretch_position', ...]  // optional
}
```

db_goblet, trap_row, db_lateral, db_tri_oh, db_skull, db_lunge, db_rdl, farmer, db_split,
db_step, db_calf, trap_shrug, db_fly, face_pull, cable_row, lat_pulldown, leg_press,

- EX-LOWER owns: biceps, triceps, forearms, core, glutes, quads, hamstrings, calves,

## 6. Sessions (stored by `js/store.js`)

```js
Session = {
  id: 's_<epochMs>',
  date: 'YYYY-MM-DD',
  status: 'planned' | 'active' | 'done',
  startedAt: ISO|null, endedAt: ISO|null,
  location: 'home',              // location id
  minutes: 45,                   // time budget the user chose
  title: 'Back & Biceps',
  targets: ['back','biceps'],    // requested target ids (group/region/preset/sculpt)
  source: 'generated' | 'manual' | 'class' | 'cardio' | 'import',
  blocks: [Block],
  rationale: [string],           // why this workout (from generator/recommender)
  notes: '',
}
Block =
 | { kind:'lift', exId, group:'A'|null,      // same letter = superset/circuit
     target:{ sets, repMin, repMax, rest, weight:number|null, reps:number|null, note:string|null },
     sets:[ { w:number|null, r:number|null, done:boolean } ] }
 | { kind:'cardio', modality, minutes, intensity, distance:{value,unit}|null, calories:number|null, done:boolean, note:string|null }
 | { kind:'class', provider:'crunch'|'other', name, time:string|null, duration:number,
     instructor:string|null, classify:ClassInfo, done:boolean }
```
Volume rule (everyone uses it via `recovery.js`): a lift set counts when `done && r > 0`.
Each counted set adds `exercise.muscles[region]` to that region. Class blocks add
`classify.muscles[region]` effective sets. Cardio and class blocks add cardio minutes.

### `js/engine/generator.js` (ENGINE-B)
```js
export function buildWorkout({
   targets,         // [targetId] group/region/preset/sculpt ids. Empty → auto via recovery.recommend
   minutes,         // total time budget INCLUDING warm-up and cardio
   location,        // location object { id, equipment:[...] }
   profile, sessions, now = new Date(),
   style = 'hypertrophy',   // 'hypertrophy' | 'pump' (short rests, supersets) | 'strength' | 'circuit'
   cardio = null,           // null | { modality, minutes, intensity }  appended as a finisher
   seed,                    // optional number for deterministic variety
   exclude = [],            // exercise ids to avoid
}) → Session (status 'planned', blocks filled, target.weight/reps from progression.suggest,
              rationale filled, title auto-generated, estMinutes on the object)
export function estimateMinutes(blocks) → number
export function alternatives(exId, { equipment, exclude = [], limit = 8 }) → [Exercise]  // same main regions, ranked
export function swapBlock(session, blockIndex, newExId, { sessions, now }) → Session (new object)
export function addExercise(session, exId, { sessions, now }) → Session
export function exercisesFor(targetId, equipmentSet, { sculptGoals = [] }) → [Exercise] ranked
```
Generator rules:
- Fit `minutes` within ±10% — **unless the workout set ceiling binds (§26): a `capped` session is short on
  purpose and exempt.** Time per set = reps×secPerRep (×2 if unilateral) + rest. Add
  setupSec per exercise and 3-6 min warm-up (shorter for short sessions).
- 15-25 min → 2-4 exercises, supersets (antagonists or non-competing), 45-60 s rests.
  45-60 min → 5-8 exercises. 75-90 min → 7-10. Compounds first, isolations later.
- Distribute sets across requested groups weighted by `need` from recovery plus sculpt goals.
  Per-group set caps per session (~8-10 for big groups, ~6-8 for small ones).
- Prefer exercises the user has done in the last ~3 weeks (consistency enables
  progression), but rotate in 1 new movement per session for variety, using `seed`.
- Exercise choices must honour equipment, `exclude`, and user rules (no back squat; prefer
  DB/cable/machine/trap bar over barbell).
- Rationale strings explain choices: 'Incline DB curl for biceps peak (long-head stretch)'.

Model requirements. Be evidence-honest, and list every assumption in `assumptions`:
- **Energy partitioning (P-ratio):** in a surplus, the fraction of gained mass that is lean depends on training stimulus, training age and body fat (Forbes: leaner people partition more to lean). Muscle growth has a **ceiling** set by training age × volume adherence × protein adequacy. Energy beyond what supports that ceiling (plus the cost of building tissue) is stored as fat. So more calories means more lean only up to a point (diminishing returns at ~+10–20% surplus for novices; Iraki 2019, Garthe 2013-type findings), after which nearly all the extra goes to fat. This is THE lesson to make visible.
- **Protein:** below ~0.7 g/lb, lean gain is reduced (scaling down smoothly toward 0.5 at 0.4 g/lb). Above ~1.0 g/lb there is no added benefit (Morton 2018 meta-analysis: ~1.6 g/kg plateau, upper CI ~2.2 g/kg).
- **Carbs/fat split:** minimal effect on body composition at equal calories and protein. Carbs support training volume and performance. Flag fat < ~20% of kcal (hormonal). Say so honestly; don't fake big effects.
- **Deficit:** lean gain is reduced. Novices and returners can still recomp; large deficits risk lean loss. **Since §23's universal amendment** the loss direction is modelled explicitly in every week with a negative balance, under every goal: Forbes' `p = 10.4/(10.4 + fat kg)`, scaled by lifting stimulus and `proteinRetentionFactor(gPerLb)`, then by `lossRateFactor(%BW/week)`, clamped to a 0.95 lean share. The goal label changes the calories, never the partition.
- **Cardio:** adds energy expenditure (by modality, intensity and bodyweight). The interference effect is small at moderate volume and grows with high-volume, high-impact running (Wilson 2012). Model it as a modest reduction of the lean ceiling above ~150–200 min/week, larger for running than cycling.
- **Body-fat projection accuracy:** track fat mass and lean mass separately (BF% = fat/weight); exclude water/glycogen shifts but note them. Calibrate TDEE with `adaptiveTdee` when data exists (raising confidence), otherwise use the formula. Use separate L/R limb measures (averaged for the model). Project limb and torso circumferences from lean distribution (by planned volume share) and fat distribution (male pattern: waist/abdomen gains and loses fat first, limbs less).
- Each series point gains `shape` fields for the 3D model: `{ neck, shoulders, chest, waist, hips, arm, forearm, thigh, calf, heightIn }`, plus `muscle: { chest, delts, lats, arms, abs, quads, calves, traps }` development scores 0..1 (from lean mass, FFMI and the volume distribution) and `bodyFatPct`.

### Cloud (Supabase over plain REST, no SDK)

section says cloud sign-in isn't set up, nothing touches the network, startup is unchanged. `startCloud` runs after the

`/auth/v1/token?grant_type=password`), refresh (`grant_type=refresh_token`, before expiry and once on a 401), password
reset email (`/auth/v1/recover`, then "Set a new password" on return), sign-out (`/auth/v1/logout`), OAuth redirect
(`/auth/v1/authorize?provider=…&redirect_to=…`, buttons only for `oauthProviders`); main.js takes `#access_token=…` /
`error_description=…` off the URL before routing. Tokens live on the account record (`cloud.session`), never in
account data or backups, and are never logged.

Data (PostgREST, `supabase/schema.sql`): `forge_state(user_id, key, value jsonb, updated_at, synced_at)` with RLS (own
rows only), `forge_push(rows)` (upsert that keeps a row only if newer), `delete_my_account()` (security definer; App Store
5.1.1(v)). One row per store key, one row per session (`s:<id>`); `value null` = deleted. `active` and `kv_*` stay on the
device. Only the active account syncs.

**Conflict policy.** Keys: last write wins by `updated_at` (the writing device's clock when the key changed). Sessions:
merge by id, newer `updatedAt` wins; a delete is a tombstone row, so it reaches other devices and the session can't come
back; an unpushed local delete beats an older remote copy. Stamps never go backwards (an edit is always newer than the
copy it edited, even if that copy came from a device whose clock runs ahead). The server refuses older rows, so two
devices pushing at once can't undo a newer change. Pull = rows with `synced_at` after the last pull (2-min overlap;
re-applying is harmless), on sign-in, app start, coming back online and returning to the app after 2+ min. Push =
everything changed since the last good push, 4 s after the last write. Known limits: device clocks decide ties; if two
devices change the same key (e.g. both log a weigh-in) before either syncs, the later change wins that whole key;
auto-planned days generated offline on two devices can both appear until the next re-plan.

**First sign-in** on an account: cloud empty → upload; this device empty → download; both have data → sheet with
**Merge both (default/recommended:** union of sessions by id, newer wins, account deletes respected; dated logs unioned
by date; settings from the account**)**, **Upload this device's data to the account** (account becomes this device), or
**Replace this device's data with the account's** (a safety copy is kept in `fgx_stash_<id>`, restorable from the
account sheet). Nothing syncs until a choice is made ("Finish setting up sync" resumes). Sign out: keep data (account
becomes local) or remove it from the device. Delete cloud account: type DELETE → `delete_my_account` → then remove or
keep the local copy. The same cloud user is never linked to two accounts on one device.

## 22. Natural testosterone therapies, interactions and the planner (2026-10-20)

Bob: "a major thing I want and most men will want is to increase testosterone **without direct testosterone
injections** — any of these therapies or pills that can do that we should accurately model based on the research
like the one that starts with a c, and we should **recommend combinations** that could be useful and attempt to
determine **combined interactions for muscle growth and fat loss**." Then: "Do what I asked for please — accurate
as possible."

This is informational modeling of published clinical literature, in the same spirit as §17: it reports what trials
measured, names the populations the results apply to, and says prescription items need a clinician. It is not
dosing advice. **Accuracy is the whole point, including reporting honestly when the modeled effect for a given man
is small or zero.** Every number carries a citation in a code comment and in
`docs/research/endogenous-testosterone.md`; every number that is *not* recoverable from a paper is labelled an
**assumption** in the code, the doc (§9 there) and the UI.

Ownership (TESTO): `js/engine/tplan.js` (new), the §22 parts of `js/data/supplements.js` and
`js/engine/metabolic.js`, the planner section of `js/ui/supplements.js`, the §22 block of `css/supp.css`,
`test/supp-testo.test.js`, e2e test `T1`, and this section.

### 22.2 The muscle-credit ceiling replaces `T_NORMAL_MID = 550`

The flat constant is **deleted**. Muscle credit follows achieved serum T on the existing Bhasin dose-response and
is bounded per item by `bodyComp` and `bcMaxLevel`:

- **measured** — trials of that item measured body composition; credit up to where they landed (hCG 870,
  clomiphene 500, sleep 900, eating enough 1,100, fat loss 700).
- **extrapolated** — no body-composition data but a measured T rise; run through the T→lean curve, bounded by the
  highest level that item's own trials reached, **labelled an extrapolation** wherever it is shown, and with a
  lower range bound of **zero** (enclomiphene 604, tamoxifen 790, ashwagandha 726, tongkat 350, zinc 500,
  cabergoline 700).
- **none** — trials measured body composition and found none; credit nothing (`tLeanShare: 0`). Aromatase
  inhibitors only.

The bound is composed the way the level is: a cause-correction item with generous evidence cannot launder a drug's
rise past that drug's own bound. **Amended 2026-10-20 — see §22.7:** `measured` is now a per-MAN judgement, not
just a per-item class, and clomiphene carries a measured bound (500) and a separate extrapolated bound (1,390).

### 22.3 Interaction engine (`combineEndogenous`, not additive)

```js
// js/engine/metabolic.js (pure)
export function combineEndogenous(parts, ctx) → {
  baselineT, causeBase, level, levelLo, levelHi, cap, capped, driverId,
  e2, e2Base, e2Assumed, e2Lo, e2Hi, e2ActionDrop, shbg, freeT, freeTBase,
  creditLevel, creditSource, extrapolated, bcNote, parts:[{ id, role, pct, delta, gateNote }], notes, warnings }
export function estradiolFatEffect(dropFrac, { weeksOn, bmi, estradiol }) → { fatDirectLbPerWeek, cumLb, loLb, hiLb, reversed, note }
export const COMBO_BONUS = 0, COMBO_BONUS_HI = 0.25, PITUITARY_CEILING = 1390, TESTIS_CEILING = 1390,
             LH_PRIMARY = 9.4, LH_PRIMARY_HARD = 18.8, LOW_T = 350,
             ASSUMED_E2 = 25, ASSUMED_SHBG = 35, E2_FAT = { … }
```

1. **Cause-correction first** (`dopamine`, `nutrient`, `lifestyle`): they raise the set-point, multiplicatively.
   *Amended 2026-10-20:* this used to be described as **shrinking** what a drug can then add. It barely does. The
   SERM curves are a roughly constant absolute rise (Hohl 2025 pooled a single +274 ng/dL across baselines
   67–303), and Keihani 2020 (n = 332) and Kim 2026 (n = 292) both found baseline total T did **not** predict the
   response. Below ~550 ng/dL a cause fix and a SERM are close to additive on the number; the taper above 550
   restores some shrinkage. The real non-additivity is between the LH-driven **drugs** (rule 2).
2. **LH-driven items share one final common path**, so the **largest wins** and the rest add `COMBO_BONUS` = 0.
   That is the measured result: Habous 2018 (RCT, 282 men) gave clomiphene +158, hCG +134, both +153 ng/dL, with
   the combination no better than clomiphene alone (p = 0.57). The optimistic bound adds 25 % — an assumption.
3. **Testicular-capacity ceiling**: **1,390 ng/dL**, both globally and for the SERM route. That is the highest
   group mean any own-axis trial has reported — clomiphene 50 mg twice daily for 8 weeks in five healthy men
   aged 26–33 (Tenover & Bremner 1991, PMID 1917692), who went from 519 to 1,390 ng/dL. **n = 5 and 100 mg/day is
   2–4× the clinical dose**, so the per-item ceilings matter more: clomiphene 1,390, enclomiphene **764**
   (Wiehle 2013 day-42 Cmax; was 800), tamoxifen **790** (Krause 1992), hCG 1,100 (an assumption; the highest
   level observed is ≈870).
4. **Primary hypogonadism attenuates, and only clear primary failure blocks.** *Rewritten 2026-10-20.* The old
   rule zeroed everything the moment LH passed 9.4. Keihani 2020 found baseline LH did not predict the response
   at all and that "normal or slightly elevated" gonadotropins still respond; Kim 2026 found a gradient
   (OR 0.82 per mIU/mL), not a cliff. 9.4 IU/L is the **European Male Ageing Study** cut (Tajar 2010,
   doi:10.1210/jc.2009-1796), which also names **compensated** hypogonadism — raised LH with a *normal* T — as a
   distinct state. So: LH ≤ 9.4 → full effect, LH is not consulted; LH > 9.4 with T ≥ 350 (compensated) → full
   effect with a note; LH 9.4→18.8 with T < 350 → linear fade; LH ≥ 18.8 with T < 350 → zero. `LH_PRIMARY_HARD`
   is an **assumption** (2 × 9.4; Kim's OR has compounded to ≈0.18 there). An AI still blocks aromatase, so it
   still costs estrogen and fat whatever the gate says.
5. **Exogenous testosterone** by any route suppresses everything axis-dependent (kept from §17, extended to the
   oral and nasal routes).
6. **Prolactin, zinc and vitamin D** corrections only help when the deficiency exists.

**Lean tracks androgen; fat tracks estradiol.** Finkelstein 2013 (doi:10.1056/NEJMoa1206168): cohort × dose
interaction P = 0.001 for % body fat, and no interaction for lean mass (P = 0.22) or strength (P = 0.91). The
per-arm kg magnitudes live only in that paper's figures, so **every coefficient in `E2_FAT` is an assumption**
(1.5 kg / 16 wk at ~90 % loss of estrogen action, range 0.5–3.0), scaled linearly by the fraction of estrogen
**action** lost — which is what reconciles Finkelstein with Burnett-Bowie 2009 ×2, Loves 2013, Mauras 2000 and
Dias 2016, where a 20–50 % estradiol drop produced nothing. A SERM's serum-E2 rise is never turned into fat loss.
`tLeanShare: 0` stays on the AIs. Sign-reversal gate: BMI ≥ 35 with estradiol ≥ 25 pg/mL switches the penalty off
(Colleluori 2020, doi:10.3389/fendo.2020.00277) — and deliberately does not model a benefit, because that arm also
lost 5.1 kg more weight. Every combined output carries a range.

### 22.7 The eugonadal correction (2026-10-20, second pass)

Bob: *"The clomiphene thing — I bet that works for anyone, bet there are hypertrophic effects to anyone, and we
should model that."* **He is right about the hormone. The muscle question is untested, and Forge now says so
instead of hiding behind a wrong zero.**

The shipped model made clomiphene, enclomiphene, hCG and cabergoline return **exactly zero** for a man with a
normal testosterone (`gate: { lowTOnly, noEffectAbove: 450 }`). That gate was fitted only to trials in hypogonadal
men and then extrapolated to zero at a normal baseline. The extrapolation was an inference, never a measurement,
and it is contradicted by:

| Study | n | Who | Regimen | Total T |
|---|---|---|---|---|
| Tenover & Bremner 1991, PMID 1917692 | 5 | **healthy** men 26–33 | clomiphene 100 mg/day, 8 wk | **519 → 1,390 ng/dL** (2.68×) |
| same | 5 | healthy men 65–85 | same | 499 → 989 (1.98×) |
| Bremner 1987, doi:10.1210/jcem-65-6-1118 | 14 | **healthy** men 22–35 | clomiphene 100 mg/day, 7 d | **490 → 980** (+100 %); SHBG 24.5 → 31.3; bioavailable fraction 65 % → **66 %** |
| Krause 1992, doi:10.1111/j.1365-2605.1992.tb01110.x | 39 v 37 | eugonadal infertile men | tamoxifen 30 mg/day, 6 mo | **490 → 790** vs placebo 530 → 560 |

**Curves.** Below 300 ng/dL the shipped curves were already arithmetically "a constant absolute rise" (clomiphene
+274 = Hohl 2025's pooled effect; enclomiphene +216 = Tienforti 2023). That shape is kept and extended, because
Keihani 2020 and Kim 2026 both found **baseline total T does not predict the response** — a constant absolute
rise automatically becomes a shrinking percentage, which is the only shrinkage the data support. Above 550 the
absolute rise tapers mildly (an **assumption**). Tamoxifen's flat `tPct: 60` becomes a constant +300 ng/dL
anchored on Krause. Forge is deliberately conservative: +275 ng/dL at a 490 baseline against measured eugonadal
rises of +300, +490 and +871.

**Gate.** `lowTOnly` / `noEffectAbove` are removed from clomiphene, enclomiphene, hCG and cabergoline (for
cabergoline the *curve* now tapers to zero at 700 instead, which is right: it gives back what prolactin took; its
`highProlactin` gate stays, because that is what Colao 2004 shows). `secondaryOnly` becomes the graded rule in
§22.3 rule 4.

**Free testosterone.** The muscle credit is now driven by free T, not total: `freeAdj = (freeT/freeTBase) /
(totalT/T0)`, capped at 1 so saturable SHBG binding can only take credit away. **The objection was checked and
does not bite**: Bremner 1987 measured the bioavailable fraction going 65 % → 66 % while total T doubled, and
feeding his numbers through Forge's own Vermeulen routine reproduces it (free-T ratio 2.01 vs total-T ratio 2.00).
SHBG did not move at all over 8 weeks (Tenover 1991) and the pooled change is not significant (Hohl 2025). The
machinery stays because it does bite for a man with a high SHBG or a larger modeled rise.

**Measured vs extrapolated is now per-MAN.** A row is `extrapolated` when the item has no body-composition data,
**or** the man's baseline is above `bcMaxBaseline` (the highest baseline that trial enrolled — Soares 2018 took
T ≤ 300, Liu 2002 took ≤ 433), **or** more than half the credited rise sits above `bcMaxLevel`. Clomiphene is
therefore `measured` for a hypogonadal man and `extrapolated` for a eugonadal one, and `tplan` ranks on the
per-man flag, not the catalogue class.

**The part that is NOT supported.** No trial has measured body composition on any SERM in a man with a normal
testosterone — a PubMed title search finds nothing besides Soares 2018 anywhere in men. The Bhasin 2001
testosterone→lean curve every extrapolation runs through was built on **exogenous** testosterone with the
gonadotropins **suppressed**, and nobody has tested whether an endogenous rise of the same size builds the same
muscle. The only two body-composition results in this class are Soares 2018 (bioimpedance, obese hypogonadal men)
and Liu 2002 (hCG: lean +2 kg and **no** gain in strength, gait or balance). Forge states this in the catalogue
entry, the per-row note, the planner's group heading and `docs/research/endogenous-testosterone.md` §8b, and
backs it up by ranking every such row on a lower bound of zero.

### 22.8 Tolerability as a first-class property, and the enclomiphene isomer question (2026-10-20, third pass)

Bob: *"I hear enclomiphene is better tolerated and has less of the estrogen effects. Study that, implement it,
and then let me know how I can get these legally, or get them at all."*

**Verdict, implemented: half supported.** "Better tolerated" — supported, on one unblinded retrospective
study. "Less of the estrogen effects" — supported for the *effects*, **contradicted for serum estradiol**,
which rises on enclomiphene about as much as on clomiphene. Full working in
`docs/research/endogenous-testosterone.md` §12; the access write-up is §13 there.

**The isomer pharmacology, now in the catalogue with numbers.** Clomiphene citrate is 62 % (trans)enclomiphene
and 38 % (cis)zuclomiphene (Wiehle 2013). Zuclomiphene is an estrogen **agonist** that barely moves
testosterone, with a half-life of ~30 days against enclomiphene's ~10 h, so it accumulates: after ≥6 weeks on
clomiphene 25 mg/day the median serum ratio is **zuclomiphene 44.0 vs enclomiphene 2.2 ng/mL, 20:1** (Helo
2017, doi:10.1111/bju.13625). Removing it is a real intervention, not a marketing distinction.

**New `model.tolerability` block** on every §22 prescription item that has data. Fields: `grade`
(`good|moderate|poor|unknown`), **`comparedWith`** (mandatory — a grade without a comparator is meaningless),
`evidence` (`rct|observational|none`), `headline`, `discontinuation: { pct, n, of, note, source }`,
`events: [{ label, pct, n, of, arm, vs?, p?, source }]`, `note`, `sources`. Helpers: `TOLERABILITY`,
`tolerabilityOf()`, `fmtRate()`, `worstTolerability()`.

Rules, enforced by `test/supp-tolerability.test.js`:
- **No rate without its denominator.** A percentage must carry `n` and `of` and must agree with them. "3 %" is
  how 2 men out of 66 gets laundered into a population statistic. A narrative row (`pct: null`) is allowed and
  must say what was observed. *(This rule immediately caught a real defect: Colao 2004's "about 4.5 %" has no
  published numerator, and it is now stored as narrative rather than as an invented fraction.)*
- **No grade without a comparator**, and a non-significant difference is labelled non-significant.
- **A combination inherits the worst grade among its items** — a stack is as tolerable as its least tolerable
  part. `unknown` never outranks a measured grade.
- Where nobody has measured it, the grade is **`unknown`** (tamoxifen). Reading silence as safety is the error
  this field exists to prevent.

Grades: enclomiphene `good`, cabergoline `good`, clomiphene `moderate`, hCG `moderate`, aromatase inhibitor
`poor` (graded on spine BMD falling over 12 randomized months — a scan, not a symptom; symptom scores actually
matched clomiphene), tamoxifen `unknown`.

**Planner and UI.** `tPlan()` rows carry `tolerability`; the grade is a **late ranking tiebreak only**, after
modeled lean − fat and evidence grade — which is exactly where Bob's question bites, since clomiphene and
enclomiphene tie at zero on the same evidence grade for a eugonadal man and were previously ordered
alphabetically. `js/ui/supplements.js` renders a tolerability badge on the planner row and in the catalogue
sheet, plus an expandable block with every rate, its denominator, the comparator arm and the caveats. Styles in
the §22 block of `css/supp.css`. e2e `T2`.

**Corrections made (each is a thing the old model got wrong, not just a refinement):**
- `e2Pct` 45 → **85**. The old value halved enclomiphene's estradiol rise on the reasoning that the estrogenic
  isomer was gone. Serum E2 rises because a SERM raises testosterone, which is aromatase's substrate; removing
  zuclomiphene does nothing to aromatase. Thomas 2023 measured **29.5 → 67 pg/mL** on enclomiphene (p = 0.003)
  against 31 → 37.6 on clomiphene (p = 0.074). Saffati's −5.92 pg/mL is a fall from an *already
  clomiphene-raised* level, not from an untreated baseline.
- **Assumption A15 replaced.** It read "enclomiphene's entire eugonadal arm = clomiphene's eugonadal response
  × 216/274". That was **circular** — Hohl's 274 is a pooled clomiphene-AND-enclomiphene class estimate whose
  10 trials include Kim 2016 and both Wiehle 2014 studies — and it misdescribed the arithmetic: the curve is
  0.787 × clomiphene's, and 0.787 × 274 = 216, which is simply Tienforti 2023's directly measured
  **enclomiphene-specific** effect. **What is inferred is the SHAPE above ~350 ng/dL, not the size**, and the
  shape rests on Keihani 2020 and Kim 2026 finding baseline T non-predictive — both clomiphene cohorts.
- The clomiphene entry now states that **+274 is a class estimate, not clomiphene-specific**; the
  clomiphene-specific pooled figure is **+333 ng/dL** (Tienforti). Forge keeps 274 as the conservative anchor.
- "Drug-related adverse events in about 21 % of men in phase 3" was read as an enclomiphene rate. It is
  **53/256 across all arms including placebo**, with no significant between-group difference.
- `tCI` [0.87, 1.13] → **[0.80, 1.45]**. The old interval was Tienforti's CI on a pooled hypogonadal mean, not
  the uncertainty of the number shown. The low end carries the isomer-matched ratio 0.65; the high end carries
  the two head-to-heads, neither of which found a significant difference (Thomas +125 vs +177, p = 0.49;
  Saffati +166 vs +98, p = 0.20, enclomiphene **higher**).
- **Real dose-response** replaces the flat `[[0,0],[100,1]]`: `[[0,0],[25,0.43],[50,0.43],[100,1]]` from
  Wiehle 2013's three arms as a rise over each arm's own baseline. Still expressed as a share of the studied
  regimen, never in mg — the §22 rule that the model prints no self-administrable dose is unchanged.
- **Ceiling re-derived and deliberately kept at 764** (A15b): that is the 25 mg day-42 **24-h Cmax**, while the
  highest *morning* group mean is 604. Dropping it to 604 was considered and rejected — 604 is the highest
  level seen in obese **hypogonadal** men at the top dose tested, not a probe of the ceiling, and hard-capping
  there would open a ~700 ng/dL gap against clomiphene that is an artefact of enrolment rather than
  pharmacology. `bcMaxLevel` stays **604** as a hard bound on muscle credit, and every extrapolated range still
  starts at zero.
- **Status string dated against FDA primary documents**: CRL **30 Nov 2015**; PCAC voted **4 yes / 8 no**
  against inclusion on the 503A Bulks List on **8 June 2022** citing lack of efficacy evidence; still
  **Category 1** on the list updated **14 May 2026**; explicitly **not** Category 2. (Category 2 does contain
  two items this catalogue models — ibutamoren/MK-677 and kisspeptin-10.)

**Still an assumption, unchanged and unfixable from the literature:** no enclomiphene trial has ever enrolled a
eugonadal man, none has ever measured body composition at any baseline, and there has never been a randomized
trial of enclomiphene against clomiphene. The Bhasin T→lean curve every extrapolated row runs through is still
exogenous testosterone with the gonadotropins suppressed (A11). Lean ranges start at zero and rows rank at zero.

### 22.9 Presentation, the scenario band and reversible causes (2026-10-21, fourth pass)

Bob: *"Right now it's barely adding anything, and I just don't think that's accurate. It helps a lot of people
a lot."* And: *"enclomiphene works for non hypogonadal males if there is some specific issue that is causing
low T ... I want the game changing results to be the default with the caveats mentioned."*

Full working in `docs/research/endogenous-testosterone.md` §14. The rules this section adds:

**A row leads with the estimate, never with the ranking score.** Every row carries
`net = { lb, lo, hi }` = the modeled central lean-minus-fat change with its range, and that is what the UI
displays. `score` remains and remains conservative (for an item whose body composition was never measured it is
pinned to the zero end of the row's own range) and is used for **ordering only**. A row must never display a
headline that contradicts its own body. Bob's clomiphene row went from `±0 lb net` (above `LEAN +4.4 lb`) to
`+4.3 lb net · 0 to +5.4`.

**Buckets are chosen by evidence class and the sign of the central estimate**, not by the sign of `score`.
`score` can be slightly negative for a row the model credits with several pounds of lean, which previously
filed clomiphene under "not in your favour".

**The accrual clock runs on effective exposure, not elapsed weeks** (`rampExposureLoss`, `js/engine/metabolic.js`).
A serum ramp may delay the muscle trajectory; it may not reduce its asymptote. Before this a 6-week titration
permanently removed ~20% of the 12-month figure (3.05 lb instead of 3.83 lb, for ever). The
exogenous-testosterone branch always behaved correctly; the endogenous branch now matches it.

**Audited and deliberately kept** (§14.2–14.6): `freeAdj` capped at 1 — measured at exactly 1.000 for every
catalogue item at every baseline, so it is inert, not a discount; the `bcMaxLevel` credit clips on enclomiphene
(604) and hCG (870), which correct admitted generosity in those items' *level* models rather than penalising
muscle twice; the zero floor on an extrapolated range; `tAgeResponse`; the above-550 `tPctByBaseline` taper.

**The planner opens with a scenario band, not one assumed number** (`scenarioBand()`, `js/engine/tplan.js`).
Four baselines across the harmonized reference range — 300 / 400 / 550 / 750, each with a normal LH, because
only the secondary/functional case is what these drugs treat — each re-running the **same** row builder against
a synthetic profile so its numbers come through `project()` like any other row. Hard rules:
- the assumed default baseline does **not** change (`averageTotalT`);
- every column is labelled a scenario, and exactly one is marked `yours` (nearest his own level);
- a man whose own LH indicates **primary** gets `notApplicable` on every column, no `yours`, and a note, because
  his own rows are correctly modeled at zero and the band must not be the one place that contradicts them;
- the band costs roughly another whole `tPlan()`, so the UI computes it from an idle callback after the first
  paint and patches `#sp-band-wrap` in place. The route must stay inside the 1.5 s budget (e2e S3).

`T_REFERENCE_RANGE` = [264, 916] and `T_REFERENCE_PCTILE` = 2.5/5/50/95/97.5 → 264/303/531/852/916
(Travison 2017, doi:10.1210/jc.2016-2935, 9,054 men, healthy non-obese 19–39). The width of "normal" is shown,
because a man at 350 is inside it and may still be well below his own set point.

**Reversible causes are first-class** (`plan.causes`): obesity, sleep debt, low energy availability, endurance
load, alcohol, raised prolactin, high SHBG masking a low free T, and opioids. Each carries a status against
what this man actually entered (`yes` / `maybe` / `no` / `unknown`) and a link to the catalogue item that
models it. Opioids are listed with `modeled: false` — a documented cause (Kafel 2025, doi:10.1111/andr.70013)
that Forge does not model and says so.

**`plan.flags`** names what in *this* profile makes a below-average baseline plausible (endurance background,
appetite-suppressing stimulant, unquantified low energy availability). It must say **plausible**, must say it
is not a fact, and must not move any number.

**"Primary"/"testicular" is never a bare term.** LH is the pituitary's instruction; a high LH with a low T
means it is being sent loudly and not obeyed; and this is not visible from outside, because the Leydig cells
are a small fraction of testis volume. The **compensated** state (raised LH, still-normal T; Tajar 2010) is
named as the real intermediate it is.

**The catalogue renders everything it stores.** `detailSheet` shows the body-composition evidence class and its
bounds, estradiol/SHBG effects, suits/not-for, `interactions` (new, tagged pharmacodynamic / pharmacokinetic /
additive), `unknowns` (new), time course, fertility, monitoring and anti-doping. Browse rows carry the evidence
grade, body-composition class and tolerability grade.

**Unchanged and non-negotiable:** zero-floored ranges wherever muscle was never measured; the note that the
Bhasin curve was built on exogenous testosterone with gonadotropins suppressed and that an endogenous rise of
the same size has never been tested; the assumptions list; the "start assumed" marker; the WADA note;
per-person `measured`/`extrapolated` labelling; prescription items marked as needing a clinician.


### 22.10 `tLeanShare` composes (2026-10-21, fifth pass)

Found reviewing §22.9: **clomiphene + aromatase inhibitor ranked above clomiphene alone** (+4.6 vs +4.3 lb net).
At 548 ng/dL the AI's modeled rise (+322) beats clomiphene's (+275), so the AI wins the "largest LH-driven
item" contest, clomiphene is subsumed and adds nothing to the level (`COMBO_BONUS = 0`) — and the whole
548 → 870, produced entirely by the AI, was credited for muscle under clomiphene's evidence bound. Adding a
drug the same engine scores at −0.8 lb alone, grades "Tolerability: poor", and has four randomized nulls on
body composition behind it (Burnett-Bowie 2009a — T 323 → 525 ng/dL with CT *and* DXA body composition and
strength unchanged at 12 months; Burnett-Bowie 2009b — spine BMD fell; Loves 2013; Juang 2014) *improved* the
row. Working in `docs/research/endogenous-testosterone.md` §15.

The rules:

- **`tLeanShare` is a share of an item's testosterone rise that may earn muscle credit**, default 1. It must be
  **composed**, not merely consulted when picking an evidence bound. `combineEndogenous`'s `run()` takes a
  `lean` flag that re-runs the identical composition over the creditable part of each rise; the result
  (`midLean.level`, exposed as `leanLevelCap`) caps the credit.
- **A suppression always has a share of 1.** `tLeanShare` says a rise does not build muscle, never that a fall
  does not cost it.
- **`creditable()` is derived from `shareOf()`**, so "can this item supply the evidence bound?" and "does its
  rise earn muscle?" cannot answer differently.
- **A measured on-therapy lab goes through the same split.** A lab cannot say which drug produced which part of
  the rise, so the creditable *fraction* the model computed is carried over. Without this, entering a lab
  reinstates the bug.
- **A zero-share item drops out of the lean LH list entirely**, so it cannot contribute a route ceiling either.
- **The invariant, pinned by test:** *adding an aromatase inhibitor never increases modeled lean*, at any
  baseline, in any combination. Every `X + AI` pairing now credits exactly what `X` credits alone.
- **The estradiol side is untouched.** The AI keeps its full `e2ActionPct`, so the combination still carries the
  Finkelstein fat penalty — which is why it is now correctly *worse* than the SERM alone rather than better.
- **A subsumed item can be the only thing earning credit.** When the driver has a zero share and a subsumed item
  does not, the row must say so explicitly, or it reads as though the lean mass came from the drug with no
  body-composition evidence.
- **The RANGE is scaled off the credited level too**, not the serum level: `leanLevelLo/Hi` (the serum bounds
  clipped by the lean-mode composition at each CI end). The aromatase inhibitor's wide `tCI [0.45, 2.2]` was
  otherwise still pushing the combination's upside above the SERM's own (0 to +10.1 vs 0 to +7.1). The scaling
  denominator is the **credited mid** for the same reason — the point estimate was produced there.
- **Every row's range must contain its own estimate** — lean, fat and net, at every baseline. This is a test,
  and adding it caught three separate leaks (docs §15.8): `freeAdj` was evaluated at the serum level rather
  than the credited one; the zero floors were applied *before* the range ends were ordered, so for a falling
  fat value the floor overwrote the real low end; and a body-composition bound could leave the interval not
  bracketing the credited mid. A row with no credited testosterone movement (an aromatase inhibitor alone,
  whose effect is entirely the estradiol fat term) falls back to the estimate rather than collapsing to [0, 0].
- **`freeAdj` is evaluated at the credited level.** Both halves of the ratio must refer to the same rise, or an
  item contributing nothing creditable can change it.


## 23. Weight-loss goal and intentional lean loss (2026-10-20)

Bob: *"the app doesn't really allow someone to lose muscle mass if they want to or if their primary goal is
weight loss. It assumes you want to maintain — need to add a feature for that."*

Forge assumed every user wanted to gain muscle or at worst keep all of it. Some people's goal is the number on
the scale: a weight class, a race weight, or simply being smaller, and they accept losing some lean mass with
the fat. This section adds that goal and makes the projection honest about what it costs. **Forge never blocks
an adult from a legal goal; it shows the costs.** Evidence and DOIs: `docs/research/weight-loss-lean-mass.md`.

Ownership: `js/engine/targets.js`, `js/engine/projection.js`, `js/engine/nutrition.js`, a one-line change in
`js/engine/recovery.js` (`groupPriority` accepts 0), and targeted edits to `js/ui/{targets,settings,projection,nutrition}.js`,
`test/weight-loss.test.js`, e2e `L1` → **GOALS**.

### The goal
`GOALS = ['recomp', 'lean_bulk', 'cut', 'weight_loss']`. `cut` keeps its meaning ("get lean, keep muscle");
`weight_loss` is "Lose weight: fat first, lean mass allowed to follow". `GOAL_INFO` (name, blurb, long) is the
single source of goal wording for every screen. `store.migrate()` is untouched: a saved `goal` is never
rewritten, and an unknown goal still resolves to `recomp` exactly as before.

### `js/engine/projection.js`
The lean/fat partition in a deficit is now modelled from three things, all of which the user controls.

> **Amendment (2026-10-20, Bob: "Better model everywhere go"), supersedes the gate below.** The partition is
> **universal**: it runs in every week where `balance < 0`, under `recomp`, `cut`, `lean_bulk` and
> `weight_loss` alike. Physiology does not read the goal field, so the same person with the same deficit,
> protein and training gets the same lean loss whatever the goal is labelled. There is one branch, no
> `lossModel` gate on the maths. What stays gated to `weight_loss` is only the goal-level machinery: the
> goal **weight** and its stop condition, `lossPlan()`-sized intake, the `result.weightLoss` block and the
> `goal_weight` milestone, the rate scan, the weight-loss-only warnings, and `result.energyAvailability`
> for men. Reported for every goal instead: `partition.leanLossLb`, `partition.leanLossFrac` (average lean
> share of each pound lost over the deficit weeks, `null` when there are none) and
> `partition.lossRatePctPerWeek`; the three-factor explanation is in `assumptions` for every goal, and the
> Nutrition lab explains what the deficit end of its sweep costs. In practice a slow, high-protein diet is
> slightly *kinder* than the old model (the rate factor floors at 0.5) and a fast, low-protein one is
> materially harsher — at 180 lb / 25 %, 26 weeks: −1,000 kcal/day at 0.5 g/lb costs 7.2 lb of lean against
> 5.9 lb before, while −350 kcal/day at 1.1 g/lb costs 0.3 lb against 0.4 lb before.

1. **Forbes' rule** (already present, now exercised and explained in the loss direction):
   `p = 10.4 / (10.4 + fat kg)` — leaner people lose proportionally more lean tissue.
2. **Rate** — `lossRateFactor(pctPerWeek)`: 1.0 at 0.7 %/week, 1.6 at 1.0 %/week, clamped [0.5, 3]
   (Garthe 2011's achieved 0.7 vs 1.0 %/week contrast).
3. **Protein** — `proteinRetentionFactor(gPerLb)`, a deficit-specific curve separate from the growth curve
   (Mettler 2010, Longland 2016, Helms 2014), plus the existing lifting-stimulus protection term.

The lean fraction of what is lost is clamped to `[0, 0.95]`: even starvation leaves some fat coming off.

**Under `weight_loss` only**, intake comes from `lossPlan().deficitKcal` (via `nutrition.lossRateDeficit`,
3,500 kcal/lb) instead of `GOAL_OFFSET`; the simulation still does proper energy bookkeeping (1,250 kcal to
build a lb of lean, 800 released when lost), so the delivered rate differs from the requested one and both are
reported. The deficit also **stops at the goal weight** as well as the goal body fat. Every other goal keeps
`GOAL_OFFSET` and the goal-body-fat stop; only the partition maths is shared.

```js
           endWeightLb, endLeanLb, endFatLb, bodyFatPct, leanShareOfLoss }],   // one lite simulation per rate
  warnings:[string] }

```

## 21b. 3D body guards (2026-10-20)

## 21c. Clothing rendering (2026-10-20)
Bob (via the 3D review): on a broad-shouldered woman the sports-top straps read as jagged dark wedges fanning out
from the neck rather than as straps, and on a heavy woman the under-bust band sat over the belly.

**Straps.** The strap was the slab `|canonical x − k| < w`. A slab is as wide as the surface is flat in x, so over
a broad, flattened shoulder it covered far more surface than intended; compensating the width with a screen-space
derivative (`|∇c.x|`, §21b) fixed the average width but made the edge sawtooth, because the derivative is a
per-quad quantity. It is now a **tube of constant radius around a centre-line**:
- `strapPath(A)` (female asset only, built once in `prepareAsset`) places seven landmark-relative anchors — top of
  the cup, mid chest, over the clavicle, across the trapezius midway between the neck and the shoulder joint, then
  down the back converging to the spine — snaps each to a real surface vertex with per-axis weights, resamples a
  Catmull-Rom through them to ≈ 0.13 dm spacing, re-snaps, Laplacian-smooths out the vertex-grid quantisation, and
  floats the result 0.07 dm off the surface along the canonical normal.
- The shader takes the distance to that polyline: the band is `2·sqrt(r² − d²)` wide with `d` the surface-to-line
  distance, so where a chord sags toward the surface the band widens slightly instead of pinching shut. On-surface
  half-width ≈ 0.115 dm ≈ 0.45 in, i.e. a ≈ 0.9 in strap that scales with the body like fabric (0.8 in at 56 in
  stature, 1.1 in at 76 in) and does not care how the shoulder is shaped.
- The cup line levels off just inside the strap (`smoothstep(0.05, 0.78 nx)`), so the strap rises out of a flat cup
  line, and panel and strap are joined with a **polynomial smooth max of the signed fields** (k = 0.13 dm) so the
  seam is a rounded join rather than a notch.

**Every fabric edge is antialiased by its own gradient.** `edge(f) = smoothstep(-1, 1, f / fwidth(f))` on a signed
field (positive inside) gives a one-pixel soft edge whatever direction the boundary runs; the old `smoothstep(a −
fwidth(c.y), a + fwidth(c.y), …)` under-softened every diagonal edge (the armpit, the shorts hem). All of it is
evaluated under the uniform `uFem` branch so the derivatives sit in uniform control flow.

**The armpit edge follows the skin weights, not the part index.** `aPart` is a per-vertex integer, so thresholding
it traced the polygonal boundary of a vertex set — a sawtooth. A new vertex attribute `aArmW` (the arm share of
each vertex's skin weights, already computed for the fit) varies smoothly across the shoulder, so the iso-contour
`armW = 0.26` is a smooth armhole. The shorts use the same edge, which also keeps the hands bare cleanly.

**Under-bust band.** The hem sits 0.22 dm below the canonical inframammary landmark (was 0.30), and the fold
itself can no longer slide onto the belly: `anthro` floors the female inframammary station at 0.035 H (≈ 2.2 in at
64 in) above the natural waist, because the fold is where the breast meets the chest wall and the ribcage bounds
it. Before the floor a 52 in bust put the fold 1.4 in above the waist and a 58 in bust 1.1 in.

**Unchanged:** §16 girths (the under-bust station still carries the modelled girth exactly), the §21b guards, and
the male body apart from the shorts-edge antialiasing — the male asset has no strap path and `bodyGeometry` is not
touched for men.

**Tests.** `test/mesh-clothing.test.js`: the path exists for the female asset only, floats inside the tube, hugs
the surface at every chord midpoint, runs front → over the trapezius → back between the neck and the deltoid,

## 24. Logging a past day (2026-10-21)

**The rule.** A date in the future is **planning**; a date in the past is **logging what happened**. They
share the builder and the class picker but never the storage: nothing written for a past day is `planned`.

### Ownership
`js/engine/retro.js` (pure: the window, the timestamps, stamping a session done), `js/ui/retro.js` (the

`scripts/scrape-crunch.mjs`. Tests: `test/retro-logging.test.js`, `test/retro-schedule.test.js`, e2e `R1`.

### How far back: 60 days
`retro.RETRO_DAYS = 60`; `retroFloor(now)` is the oldest loggable date and `canLogPast(date, now)` is the
single gate (today counts — "I did it this morning"). Long enough to catch up after a holiday or a few
forgotten days; short enough that a mistyped date cannot silently rewrite the months of history that
progression, the projection and the body model read. Every date input is bounded by `min=retroFloor()`
`max=today`, and every entry point re-checks `canLogPast` before writing.

```js
// js/engine/retro.js (pure, DOM-free)
export const RETRO_DAYS = 60;
export function retroFloor(now = new Date()) → 'YYYY-MM-DD'
export function canLogPast(date, now = new Date()) → boolean        // the one gate
export function retroReason(date, now) → null | 'bad-date' | 'future' | 'too-old'
export function retroTimes(date, { time, minutes, now }) → { startedAt, endedAt }   // both ON `date`
export function markLogged(session, { now }) → session              // status 'done' + stamps + blocks ticked
```

### What a retro log stores
`status: 'done'`, `date` = the day it happened, `startedAt`/`endedAt` **on that same calendar day**
(the class's own time when we know it, else 18:00, clamped so a late class cannot spill past midnight;
`date === today` ends at *now*), non-lift blocks `done: true`, and no `plan` field. Lift sets are never
invented — a lift set still only counts when the user logged `done && r > 0` (§6), so a retro lift goes
through the per-set logger: an `'active'` session with `startedAt: null`, which `js/ui/session.js` shows
an editable date for (not a running clock) and whose **Finish** applies `retroTimes` to its own date.

Those stamps are the whole trick: `recovery.sessionTime` only trusts `startedAt`/`endedAt` when they fall
on the session's `date`, so the work lands on the right day for "days since" and the rolling 7-day volume;
`planner.weekPlanSummary` and `recovery.weekSummary` bucket by `date`, so a workout logged for last Tuesday
counts toward **that** week's coverage and not this one; History, the Body tab and the projection's
history drivers all read the same `status === 'done'` + `date` pair and need no special case.

### Where you can do it
- **Plan, past day card** — "Log what I did" (`[data-retro="<date>"]`) opens the shared sheet: log a class,
  build what you did, log exercises freely, log cardio, or (when a plan was left unlogged) "It was a rest
  day", which clears the missed plan so the day reads *Rest* instead of *Skipped*. **No rest marker session
  is written** — an unlogged past day with no leftover plan already means rest, and a fake `done` session
  would inflate History counts and the projection's adherence driver. Already-logged lines keep opening the
  session, where they can be edited or deleted.
- **History** — "＋ Log a past workout" in the page head (and on a selected empty day), since that is where
  people look after the fact. Without a day in hand the sheet asks for one (default: yesterday).
- **Today** — "Log something I already did" is unchanged except that its date is bounded by the window.
- **The date builder** (`#/today?date=…`) now accepts a past date and runs in **log mode**: same
  recommendations and build flow (engines see `contextFor(date)`, i.e. the history as it was *then*), the
  header says *Logging*, and the primary button is "✓ Log it on <day>" → the per-set logger. "Save to plan"
  is not offered for a past day.

### Class schedules: merge, never overwrite
`scripts/scrape-crunch.mjs` merges the fetched days into `data/crunch-schedule.json` instead of replacing
it, so the file accumulates history:

- **past days** are kept (the endpoint never returns them) and **compacted** to the fields the app shows
  (`name`, `time`, `start`, `duration`, `instructor`) — `classify` is recomputed on load by
  `normalizeSchedule`, and `description`/`id`/`room`/`category` are never displayed, so this is lossless
  and keeps the committed file and its daily diff small;
- **today** is a union of stored + fetched, because the occurrences endpoint drops classes that have
  already started and a midday run must not delete the morning;
- **future days** are taken from the fresh fetch outright, so moved or cancelled classes disappear;
- anything older than `KEEP_BACK_DAYS = 90` is pruned (90 covers the 60-day logging window with slack,
  ≈ 50 KB of compacted days).

The merge is pure and **idempotent** (`mergeDays`, `buildPayload`): same inputs → byte-identical file apart
from `fetchedAt`, which the Action's diff already ignores. A fetch that parses zero classes still exits 2
and leaves the stored file alone.

`js/classes/crunch.js`: `normalizeSchedule` keeps every day in the file; `stale` keeps meaning **"we have
no data at or after today"** (never "this file contains old days"); `date` falls back to the next day we
have, else the most recent one; `dayFor(sched, date)` serves one day.

`js/ui/classes.js`: with a past date the picker shows that day's actual classes ("✓ I did this class") and
always offers **"Log a class by name"** with chips from everything the schedule file has ever held plus
`classify.CLASS_CATALOGUE` (known Crunch Allen classes + generic types), so a day we never cached — anything
before this shipped — degrades to typing or tapping a name rather than dead-ending. Credit comes from
`classify()` either way, so a typed class is credited exactly like a scraped one.

### 25.1 Every constant is sourced or labelled

`setResponse` consumes **fractional** sets — indirect work counted at the exercise's own muscle weight,
which is what `recovery.sessionVolume` already produces and what Pelland found to be the best-supported
quantification. The units of the published curve and of Forge's input are the same units.

### 25.2 Specificity is a contract, not an emergent property

The model MUST satisfy all of these (asserted in `test/muscle-specificity.test.js`):

1. A group with **zero planned sets gains nothing**, under every goal (`setResponse(0) = 0`).
2. In a deficit, a group with zero sets **loses roughly its anatomical share** of the lean loss, while a
   trained group is spared. Lean loss is distributed by `share[g] × (1 − systemic × maintenanceProtection(sets[g]))`,
   not by `share[g]` alone. This replaces §23's single whole-body `min(1, respW/0.7)` protection term; the
   §23 partition itself (Forbes, `lossRateFactor`, `proteinRetentionFactor`, the 0.95 clamp) is unchanged,
   and a uniformly trained body gets the identical answer.
3. A group at **maintenance volume holds** rather than shrinks. Maintenance saturates at ~2-3 fractional
   sets/week, where growth is still climbing past 20 — the Bickel/Spiering finding.
4. **2× the sets diverges visibly** over 6-12 months, at roughly √2× the growth, and the gap widens with time.
5. Emphasis reaches the **tape** (`series[].shape`) and the **3D body** (`series[].muscle`): a year of
   arms-only raises arm girth and leaves thigh and calf flat; legs-only does the reverse.

### 25.3 The ceiling binds per muscle, not wholesale

`ceilingFactor` is evaluated at each group's **own** distance from the limit, using
`ffmiEq[g] = ffmiOf(L0 + G[g]/share[g])` — the whole-body FFMI you would have if every muscle were as
developed as that group is now, which is the same extrapolation `muscleAt()` shows the user. The hard guard
is likewise per-group (`share[g] × L0 + G[g] ≤ share[g] × Lcap`); the old global rescale
(`for (const g of GROUP_ORDER) gG[g] *= f`) is gone, because scaling every muscle by one factor is exactly
the wholesale behaviour Bob rejected. Both are strict generalizations: with equal volume everywhere they
reduce to the previous global formulas. Total lean still can never pass `Lcap`, and must approach it
asymptotically (tested to the 8-year horizon).

`mods.partitionShift` still rescales all groups proportionally. That is kept deliberately: it is a
whole-body energy-partition effect with no per-muscle structure, and a proportional rescale preserves
emphasis.

### 25.4 `project()` output additions

### 25.6 Cardio what-if calories are compensated

`cardioDeltaMin` used to pass 100 % of the added cardio's calories into energy balance. It now carries
Careau 2021's exercise energy compensation: only ~72 % of the added exercise's **net** cost (gross minus the
resting burn those minutes would have cost anyway — compensation is measured on ACTIVITY expenditure) reaches
total expenditure. Three rules: **delta only** (the baseline plan's calories are already inside the formula
TDEE and inside `adaptiveTdee`'s calibration, so discounting them would double-count), **symmetric** (removing
cardio gives back ~72 % too), and **minutes stay real** (only calories are discounted; minutes still drive
interference and the resting-burn offset). For Bob at a fixed intake, +240 min/week of easy cycling over 26
weeks goes from −8.0 to −6.8 lb of fat.

Separately: the resting-metabolic-rate formula `370 + 21.6 × lean kg` is **Cunningham 1991**
(doi:10.1093/ajcn/54.6.963), not Katch-McArdle (a skinfold body-composition method). The formula is unchanged;
the name was wrong in the code, the comments and the user-facing `assumptions` text, and is now right.

### 25.7 Known gap: unit vs group granularity (not fixed here)

The planner and `targets.js` plan and cap volume per **VOLUME_UNIT** (16 units, e.g. side delts separately
from rear delts); the projection models growth per **GROUP** (11 groups), where a group's set count is the
max over its regions rather than the sum of its units. Single-unit groups agree exactly; `chest`,
`shoulders` and `back` read 10-33 % lower in the projection than the planner's unit totals. The projection
therefore cannot resolve emphasis *within* a group. Fixing it means giving each VOLUME_UNIT an SMM share in
`js/data/muscles.js` and moving the growth model to units, keeping the group rollup for display. Measured
numbers and a second cohesion gap (`TYPICAL_SHARE` still derived from the legacy group minimums) are in
`docs/research/growth-model.md` §14.

### 25.8 Performance budgets

The two projection performance tests (`test/long-horizon.test.js`, `test/nutri-model.test.js`) warm the exact
code paths they time and assert on the **minimum of 3 samples**, not one cold reading. A single wall-clock

### 26.1 The workout set ceiling

**Why it happened.** The fitter turned minutes into sets: `desiredSets` = budget ÷ `perSet` (Time-saver 75 s,
Hypertrophy 115 s), `tune()` added sets and exercises until the estimate met the budget, and the
complement-group loop added whole muscle groups to fill what was left. Per-muscle caps existed but nothing
capped the workout. Measured before the change at Crunch, auto targets: Time-saver 45′ → 35 sets, 75′ → 60,
Pump 90′ → 74, Circuit 90′ → 90.

**The setting** (read and written through `js/engine/targets.js`, §18):
```js
profile.sessionSetCap                       // number, working sets per workout; absent = default
targets.LIMITS.sessionSetCap = [12, 50]     // targets.SESSION_CAP_DEFAULT = 30
targets.sessionSetCapOf(profile) → number   // the resolver every engine calls
resolveTargets(p).training.sessionSetCap
applyTargetChange(p, { training: { sessionSetCap: 24 } })   // clamped; null resets to the default
// needsReplan() and describeChange() ("at most 24 working sets a workout") include it.
targets.SESSION_CAP_INFO = { short, label, text, evidence:[{ claim, source }] }   // the in-app "why"
```
UI: Settings → Training defaults → "Most working sets in one workout" (slider 12–50, `setTargets`, re-plans).

**What counts.** A working set is a row of a non-skipped lift block (`target.sets` when a block has no rows),
the same rule as §18's set-count semantics; warm-ups are never stored, so never count. `generator.workingSets(s)`.

**Generator contract** (every style: the five built-ins and every custom style):
- `desiredSets` never aims past the ceiling. The greedy fill, `tune()` (normal and relaxed) and a final
  enforcement pass refuse any add — a set, an exercise — that would pass it (checked on the materialized plan,
  because pairs equalize set counts).
- When the ceiling is what stops it, leftover time goes **first to longer rests, within the style's own
  `restFlex` allowance** `[lo, hi, hiRelaxed]` (Time-saver up to ×1.2, Hypertrophy ×1.5, custom styles none),
  **then the workout finishes early.** No complement group is added once the ceiling binds.
- The session carries `capped = { sets, cap, freedMin, restScale }` (`freedMin` = budget − estimate, ≥ 0) and a
  rationale line from `generator.capLine()`: *"Capped at 30 working sets: finishes ~14′ early. Past this, extra
  sets mostly add fatigue (a convention; change it in Settings)."* A capped session is **exempt from the ±10%
  time fit** (§8) and is never `poolLimited`. `buildWorkout({ setCap })` overrides the profile.
- Result at the default 30, Crunch, auto targets: Time-saver 60′ → 30 sets, ~44′; Hypertrophy 60′ → ~30 sets,
  ~60′ (barely changed); Hypertrophy 90′ → 30 sets, ~81′ with rests ×1.5.

**Per-muscle caps, made real.** `generator.muscleSessionCap(group, minutes, starred)` = the generator's own
per-group cap (8 small / 10 big, ×1.2 at 75+ min) raised to the planner's priority allowance of 12 for a
starred group, counted on **direct sets** (sets of moves whose prime mover is that group). The baseline
fitter leaked past its caps — pair equalization bumped a 2-set add to 3, and the relaxed pass ignored caps (a
45-min Pump chest day had 19 direct chest sets; a 75-min Time-saver chest day 24, both at seed 5). The fitter now refuses any
add that pushes a muscle past `muscleSessionCap`, and the overload warning uses the same function, so Forge
never warns about a workout it built itself (pinned by test across styles, places, targets and planned weeks).

**Ordering fix found on the way.** Each group's opener (the staple `scoreEx` forces first) now stays first among
that group's moves of the same category; a higher-fatigue compound picked later (a rack pull after the row
that opened back) no longer sorts ahead of it. This is the PLAN-FIX "first exercise is a staple" contract,
which a seed-dependent test had only been passing by luck.

**Planner** (§12): no planned day passes the ceiling — `liftDay` builds under it and `balanceVolume` never adds a
set or exercise that would pass it, so a day is lengthened only as far as the sets under the ceiling need.
Binding reasons stay true of the day (§18):
- per day: muscle at its own per-session cap → `session`; day at the ceiling, or a legal candidate kept out only
  by it → **`ceiling`**; then time; then the first real blocker.
- per week: `ceiling` (*"your 30-set workout ceiling on every lift day"*) only when every lift day holds within a
  set of it; otherwise **`ceiling_some`** (*"… on 2 of 3 lift days"*, counts from the plan).
  `TARGET_WHY_TEXT[why](pol, { setCap, ceilDays, liftDays })`.
- `weekPlanSummary`: `minimums.binding` can be `'ceiling'`; the shortfall warning says *"(every lift day is at your
  30-set workout ceiling: add a lift day)"*; `capacity` gains `{ setCap, liftDays, maxSets }`; the priority
  capacity warning names the ceiling when it is what binds. `decideFlex` values a lift day at
  `min(minutes × 0.33, ceiling)` sets.
- Consequence: with very high targets (all sliders 2×) four 30-set days no longer reach ≥60% of targets; the week
  says so (`ceiling`) instead of lengthening every day to 90′.

**Overload warning for workouts the user builds or edits** (advice only, never blocks):
```js
generator.sessionLoad(session, profile) → { sets, cap, over, excess, muscles:[{ group, name, sets, cap }], heavy }
generator.trimToCap(session, cap | null, { profile, sessions, now, muscles }) → { session, removed:[{ exId, from, to }] }
```
`trimToCap` reuses the fitter's need measure (desired sets per region from recovery need × priority × sculpt
goals) and its drop ordering (a pattern duplicate before a lone fly, compounds protected a little):
(1) sets above each exercise's default for the style come off the least-needed exercises first; (2) then whole
least-needed exercises go while the excess covers them (2+ exercises kept); (3) then single sets down to 2.
`muscles:true` then trims any muscle still past its cap. Logged sets are never removed; a superset left with one
member becomes a straight set with its own rest. UI (`js/ui/overload.js`): Today's preview, Plan's day sheet and
the live workout header show *"Heavy workout: 48 working sets, your ceiling is 30."* + **Trim to 30**, or the
per-muscle line + **Trim triceps to 12**, or — for an unedited capped build — the capped line.

**Honesty labels.** The ceiling is a **convention**, labelled so in Settings and in every warning. Per the
weekly-volume audit §8.5, per-session caps are a fatigue / set-quality / time heuristic, not a measured
hypertrophy ceiling: Pelland et al. 2025 (Sports Med 56:481, doi:10.1007/s40279-025-02344-w) report
diminishing returns but no per-session plateau, and the honest argument is Calzavara & Barroso 2026 (J Strength
Cond Res, doi:10.1519/JSC.0000000000005665): nine weekly quad sets in one session or three grew the quads the
same, with 58–76% more volume load when spread. **The number 30 has no source**; at Hypertrophy's ~115 s a set
it is about an hour of work, so it leaves the default 60-minute Hypertrophy workout essentially unchanged and
stops the denser styles turning spare minutes into extra sets. The per-muscle numbers (8 / 10 / 12) are the
same convention (§18 amendment, audit §8.5: "the specific 8 / 10 / 12 split has no source").

### 26.2 "Something's hurting"

**Shape and storage.**
```js
profile.issues = [{ id:'is_<ms>', area, group?, side:'left'|'right'|'both', severity:'mild'|'moderate'|'severe',
                    started:'YYYY-MM-DD', note, resolvedAt:'YYYY-MM-DD'|null, checkedAt?:'YYYY-MM-DD' }]
// area: shoulder | elbow | wrist (wrist/forearm) | neck | upper_back | lower_back | hip | knee | ankle (ankle/foot)
//       | muscle (+ group = a muscles.GROUPS id). side only for sided areas (else 'both').
```
Stored **on the profile**: the least invasive correct option. The profile is already one account-scoped key
(`fg_profile` / `fga_<id>_profile`, §19), so issues follow account switching, test-mode personas (blank until
logged), backups (`exportAll` / `importAll`) and cloud sync with no change to `js/store.js`. Known limit, as for
every profile field: two devices editing the profile before either syncs → the later write wins the whole key.
Resolved issues stay (with `resolvedAt`) for the record; only active ones affect anything.

**One write path** (§18): `applyTargetChange(p, { issues: patch })` → `issues.applyIssuePatch`, patch =
`{ add } | { update:{ id, … } } | { resolve:id } | { check:id } | { remove:id }` (+ optional `date`). An update
applies its valid fields and ignores the rest. `resolveTargets(p).issues` lists the active ones. `needsReplan`
fires on add / update / resolve / remove (area, muscle or severity changed), not on `check` ("still hurting")
or a note edit, so logging an issue re-plans the upcoming auto days through the usual `setTargets`.

**Severity → effect** (`issues.SEVERITIES`):
| Severity | Shown as | Exercise choice |
|---|---|---|
| mild | "Twinge — train around it" | tier 3 (loads it hardest) excluded; tier 2 kept at a ×0.35 score penalty |
| moderate | "Avoid loading it" | tiers 2 and 3 excluded |
| severe | "Avoid loading it" + *"Sharp pain, swelling, numbness or pain at rest: stop and get it checked."* | tiers 2 and 3 excluded |

Every sheet carries `issues.NOT_A_CLINICIAN`: *"Forge is not a clinician: logging this only changes which exercises
it picks. It does not diagnose or treat anything."* No diagnosis words, no treatment advice (pinned by test).
`side` is recorded and shown but does not change selection (a unilateral move is programmed for both sides).

**The stress map** (`js/data/stress.js`). `stressOf(ex) → { shoulder, elbow, wrist, neck, upper_back, lower_back,
hip, knee, ankle }` each 0–3: 0 none · 1 incidental · 2 clearly loads it · 3 loads it hardest. Derived **by rule**
from pattern, muscles, equipment and id keywords (dips, close-grip, skull / overhead extensions, preacher and
reverse curls, upright rows, bent-over rows, free-weight hinges, jumps, push-ups on the hands, hanging work …)
plus muscle-credit floors (a lower-back prime mover loads the lower back) and a ~20-entry override list; not
hand-annotated per exercise, so a new exercise gets a map. A muscle issue uses the exercise's own credit to that
group (≥0.75 → 3, ≥0.5 → 2, >0 → 1). **The tiers are a coaching convention** (which joints a pattern loads,
conservative where a move is commonly reported to aggravate an area), not measured joint forces. Pinned cases:
elbow drops skull crushers / close-grip bench / dips, never the leg press; lower back (moderate) drops
deadlifts, RDLs and bent-over rows but keeps supported work (machine press, chest-supported rows, leg press);
knee drops squats, lunges and leg extensions even at mild.

**Where it is honoured.** `issues.issueFilter(active) → { blocked, penalty, why(exId) }` is read by: the
generator's pool (blocked out, mild penalty in the score); `alternatives()` and `exercisesFor()` (`issues`
option); the planner's top-up adds and swaps (merged into its avoid set); the swap / add sheets (hidden from
the suggestions with "N more hidden: they load your left elbow"; search still finds them, marked "⚠ loads your
…", because an explicit pick is the user's call). `addExercise` / `swapBlock` stay unconditional (they apply a
pick the user already made). When an issue leaves nothing for a requested group here, the rationale says so —
*"Biceps: every biceps exercise here loads your left elbow (moderate), so it is left out today"* — and if no
requested group is left, its complement groups that the issue spares are trained instead (*"So this works back &
shoulders instead, which spare it"*); if none, *"Nothing here trains that without loading it…"*. Never a silent
empty workout. A fill-in group is never one the issue leaves nothing for.

**UI** (`js/ui/issues.js`). Today: a low-key "🩹 Something hurting?" link and one chip per active issue (tap →
edit sheet with **Feels better**, which resolves it); an issue logged or last confirmed ≥7 days ago
(`issues.CHECK_DAYS`) shows one **"Still hurting?"** card (Still hurting → `checkedAt`, asks again in a week;
Feels better → resolved). Body: the same list ("Working around" / "Aches & pains"). Live workout: ⋯ → **This
hurts** → the areas that exercise loads, hardest first (`issues.areaOptionsFor`), side, severity → logs the issue
and swaps to the alternative that spares every active issue and loads the logged area least (logged sets stay
with the old exercise; no safe swap here → the exercise is skipped, said in a toast).

**Known gaps.** `recovery.recommend` (Today's "What should I train?") is not issue-aware; the generator
substitutes when a recommended group is fully excluded, and says so. The tiers are not graded by side or range of
motion.
